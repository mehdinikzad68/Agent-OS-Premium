3. RECOMMENDATIONS — NOT APPROVED IMPLEMENTATION

Item 1: host/control and executor environment
- Keep the trusted control service on native Windows initially; use the existing Docker/WSL2 installation as the first candidate for a disposable Linux worker, only if the chosen repository/test is Linux-compatible.
- Windows-installed Hermes/DSH binaries do not automatically exist inside a Linux container. Container runtime provisioning and version verification require later, separate approval.
- If the mission requires native Windows behavior, reconsider a disposable Windows VM instead of treating a worktree or ordinary WSL distribution as a fallback security boundary.

Item 3: isolation
- Current conclusion: PRESENT CANDIDATE, NOT VERIFIED CONTAINMENT.
- Before real work, require approved tests of host-file and credential isolation, network denial and cleanup/interruption behavior. Do not infer these from registration, container existence or exit code zero.
- Proposed worker restrictions: only the disposable mission copy; no host home, credential directories, control database or Docker/management socket; no privileged mode or broad host mounts; restricted user/capabilities.
- Begin enforcement tests with a fake adapter and no network. Real model access subsequently needs a separately approved, constrained route that cannot bypass scoped egress approval.
- Plain WSL, a working directory, an approval prompt and shell policy are not sufficient boundaries. Docker is also not an absolute defense against kernel/hypervisor compromise; workload trust and required isolation strength still matter.

Item 5: control-service stack
- Recommend Python 3.13 + SQLite for the first small service, initially tested with standard-library tooling and a fake adapter. Defer a web framework and dashboard package installation; Next.js can remain the later UI candidate.
- Reasons: SQLite/process/control logic fit a small Python service; the documented DSH SDK has a direct Python interface with event notifications; no TypeScript-to-Python bridge is needed if that SDK proves suitable.
- Trade-offs: a later TypeScript UI creates a two-language system; boundary schemas need explicit validation/versioning; process lifecycle/cancellation still requires careful Windows testing; SDK installation/version compatibility is not yet established.
- An all-TypeScript service simplifies shared UI types and process/event handling. It does not solve ACP telemetry/resume limitations; adopting the Python SDK later would add a bridge.
- This recommends a language, not an SDK install, framework commitment or authorization to launch workers. Python 3.13 for the control service does not change Hermes' own Python environment.
